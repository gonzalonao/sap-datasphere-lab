# Naming convention

Applies to every object created in the tenant. Introduced in unit 01; extended as new object
types appear (rows marked *planned* are reserved, not yet used).

## Rules

- **Technical names:** `UPPER_SNAKE_CASE`, letters, digits and underscores only, starting
  with a letter. No spaces, no dots, no person/company/tenant identifiers.
- **Business names:** plain English, Title Case, readable by a report user. Always filled in
  — SAC and Power BI show them, not the technical name.
- **Pattern:** `<TYPE>_<DOMAIN>_<ENTITY>[_<QUALIFIER>]`, with `NW` as the domain for
  Northwind. The type prefix makes the object kind obvious in lists and lineage.
- **Singular entity names for dimensions** (`DIM_NW_CUSTOMER`), plural for tables that mirror
  a source entity set (`LT_NW_ORDERS`), so tables read like the source and dimensions read
  like business concepts.
- Max length: keep technical names well under the 50-character tenant limit
  (⚠ verify the limit in the tenant).

## Object types

| Object | Prefix | Example | Notes |
| ------ | ------ | ------- | ----- |
| Space | `NW_<PURPOSE>` | `NW_LAB` | Space IDs are tenant-unique. If taken in a shared training tenant, append a short suffix (e.g. `NW_LAB_07`) and log it in `decisions.md`. |
| Folder | `NW_<PURPOSE>` | `NW_LAB` | Data Builder folder standing in for a space while working in a shared space. Same pattern as space IDs so a later move to a real space keeps the name. |
| Connection | `CN_<SOURCE>_<PROTOCOL>` | `CN_NW_ODATA`, `CN_NW_AZSQL`, `CN_NW_S4SBX` | One connection per source system and protocol. `S4SBX` = the SAP S/4HANA Cloud sandbox API. |
| Local table | `LT_<DOMAIN>_<ENTITY>` | `LT_NW_ORDERS`, `LT_NW_AZ_ORDERS` | Loaded from file upload, or the target of a flow. `AZ` marks tables landed from the Azure SQL source (`LT_NW_AZ_SALES` from `TF_NW_SALES`, `LT_NW_AZ_EMPLOYEES_CLEAN` from `DF_NW_EMPLOYEES`). |
| Remote table | `RT_<DOMAIN>_<ENTITY>` | `RT_NW_ORDERS` | Federated or replicated; the data-access mode is set in the object, not the name. |
| Relational view | `V_<DOMAIN>_<ENTITY>` | `V_NW_SALES_VS_TARGET` | Intermediate / cleansing view (Relational Dataset). First used in Phase B. |
| Dimension view | `DIM_<DOMAIN>_<ENTITY>` | `DIM_NW_CUSTOMER` | Semantic usage *Dimension*. |

## Shared spaces

Technical names are unique per **space**, not per folder. When working in a shared space,
search for the name before creating an object; the `NW_` domain token keeps collisions
unlikely.

## Columns

- Keep source column names where the source is clear (`OrderID`, `CustomerID`) so lineage
  back to the source is obvious.
- Calculated columns and measures created in Datasphere use `UPPER_SNAKE_CASE`
  (`ORDER_DATE`, `REVENUE`), which visually separates "derived here" from "came from source".
- Business names for columns are Title Case with spaces (`Order Date`, `Revenue`).

## Exceptions

- **Time dimension objects** are generated by Datasphere under fixed technical names
  (`SAP.TIME.*`). They are not renamed; the space-level time settings are documented in the
  unit that creates them.
- **SAC stories and other consumer-side artefacts** are named in plain English
  (`Northwind Sales Overview`) because they are shown to end users. They are saved in a
  private SAC folder `NW_LAB` under *My Files*, mirroring the Datasphere folder.
